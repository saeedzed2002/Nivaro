# Local release incident procedures

Use the project name and full overlay list from [the local release guide](LOCAL_RELEASE.md). Record the release revision, failing service, request or event ID, timestamp and last confirmed state. Keep log excerpts free of secrets, session cookies, private messages and image data.

| Symptom | Check and recover |
| --- | --- |
| Staff sign-in fails | Confirm Identity health and use the staff sign-in route. On the target environment use the interactive Identity `change-admin-password` command for authorized recovery. It revokes staff sessions. Bootstrap is for a new installation and refuses a second administrator bootstrap. [Identity operator commands](../../services/identity/README.md#run-and-inspect) |
| Token verification fails across services | Check the `kid`, clock and served `/.well-known/jwks.json` against the selected release settings. See the signing-key rotation steps below. |
| Image remains pending or fails | Identify the owning Catalog or Identity record, then check its dispatcher, worker and RabbitMQ queue. Diagnose storage or decode failures before requeueing the affected item through the supported service path. Verify the previous ready image still serves until replacement succeeds. Keep the previous files until a successful activation and reference check. [Catalog media operations](../../services/catalog/README.md#p04-catalog-media-runtime) · [Identity media operations](../../services/identity/README.md#private-profile-images) |
| An order event fails delivery | Match its event ID against the publisher outbox or consumer receipt and error queue. Determine whether the database effect already committed before considering a replay. Preserve the original event ID so duplicate handling remains effective. Check the resulting order, stock or cart state. [Orders event procedures](../../services/orders/README.md#durable-reservation-expiry) |
| A payment remains ambiguous, arrives late or needs refund | Start from the staff Payments workspace. Check the provider evidence, amount, currency and already recorded ledger state. Reconcile the same attempt before starting another operation. Use the permission-scoped refund operation only after reviewing the remaining captured balance. Verify the Payments ledger and the linked Order result. [Payments state and operator reconciliation](../../services/payments/README.md) |
| Support messages stop appearing live | Confirm Support, PostgreSQL and Redis health, then inspect the WebSocket handshake and last applied sequence. Reconnect and page committed history from that sequence through `sync.request`. Retry an unacknowledged send with its original `client_message_id`. If two replicas disagree, check the database history first, then verify Redis fan-out connectivity between the replicas. [Support protocol and checks](../../services/support/README.md) |
| A release migration fails or state must be recovered | Stop traffic and keep the current data available for inspection. Check application/schema compatibility and restore the selected pre-migration bundle into a separate Compose project when required. Verify before switching traffic. [Backup, restore and rollback](BACKUP_RESTORE.md) |

## Rotate the Identity signing key

Rehearse this on a separate release project first. Preserve the current signing key in protected storage and export the current public JWKS. Generate a replacement RSA private key of at least 2048 bits in protected storage. Configure an Identity-only read-only mount for the public overlap JWKS and point `IDENTITY_JWT_PREVIOUS_PUBLIC_KEYS_FILE` at that container path. Set the existing signing-key secret to the replacement and recreate Identity so it mounts and reads both files. The [Identity security contract](../../services/identity/README.md#security-contract) describes access lifetime and verification.

Confirm that JWKS publishes the old and new `kid`, that new sessions use the new key, and that an unexpired old token still works. Check staff and customer permissions through the gateway. Keep the overlap until old access tokens and downstream key caches have expired, then remove the old public entry and exercise the boundary again. A rollback must also preserve the public key for whichever sessions were issued during the attempted rotation. Rotating the OTP or CSRF pepper is a separate operation with different session consequences.
