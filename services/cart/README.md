# Nivaro Cart

The service owns its PostgreSQL database and stores guest/customer owner identities, per-market carts, stable line IDs, component groups, private build drafts and idempotency records. A composite foreign key prevents assigning a line to a group in another cart, and a partial unique index keeps standalone lines unique per variant while allowing that variant in multiple groups. Transferred group provenance survives source draft deletion.

The service exposes liveness/readiness, `POST /api/v1/cart/session` (guest bootstrap), `GET /api/v1/cart/session` (guest synchronizer token) and `GET /api/v1/cart?market=ir|international` (private owned state). Session bootstrap requires an allowed Origin and `X-CSRF-Request: 1`; reading the token requires that header and rejects foreign origins/cross-site requests. Responses are `no-store`. Guest cookies are random 256-bit values, HttpOnly, SameSite=Lax and Secure in release; only their SHA-256 digest is persisted. Server-side guest CSRF state is independent of the bearer cookie. Thirty inactive days expire ownership without deleting the source cart; explicit expired-session UI recovery and cleanup remain pending.

Customer reads verify RS256 issuer/audience/kind/session claims using identity JWKS, then call the dedicated identity customer introspection route with a short-lived request-bound service credential. Revocation/disable is checked freshly. Origin and session CSRF are validated for mutating calls. A present invalid/revoked customer cookie or unavailable identity during customer authorization cannot silently fall back to a guest cart. Customer IDs and cart ownership never come from a query parameter or submitted cart ID. The guest cart remains separate after login until the explicit idempotent merge workflow is implemented; logout returns to guest ownership, never to the account cart. The upcoming frontend must coordinate access refresh before cart work for a known signed-in session, because refresh cookies are deliberately restricted to identity's refresh path.

The local Compose stack mounts a dedicated `cart_identity_service_key` for both `CART_IDENTITY_SERVICE_KEY_FILE` and `IDENTITY_CART_SERVICE_KEY_FILE`. The local secret helper prepares it, and `cart-db-init` provisions the DB role before `cart-init` applies migrations. Configure `CART_CATALOG_URL` for the catalog HTTP boundary. The loopback gateway routes cart/build APIs. `scripts/Verify-CartGateway.ps1` verifies this against a separate disposable stack on port 8082.

After login, `GET /api/v1/cart/merge?market=ir` returns the current browser's guest cart ID, revision and counts when that market has selections. `POST /api/v1/cart/merge` requires the guest cookie, authenticated customer session, customer CSRF token and allowed Origin, `Idempotency-Key`, market, and both expected cart revisions. The key is scoped to the customer and bound to the guest, market and revisions. An exact retry returns the stored receipt while the guest cookie is valid. The merge moves groups and their lines intact. Matching standalone lines join under the existing customer line ID. Version or limit conflicts roll back the transaction. Catalog validation and estimates occur on subsequent cart reads. Merge neither reserves stock nor transfers saved drafts. The other market stays separate.

For an expired or invalid guest cookie, `POST /api/v1/cart/session?recover_expired=true` can start a new empty guest session after the existing origin and custom-header checks. A valid guest session is reused, and expired cart rows are retained. The frontend should request recovery only after the user chooses to start a new cart.

Guest and customer sessions can save and list private drafts through `POST /api/v1/builds` and `GET /api/v1/builds?market=ir`. List pagination uses the last returned ID as `after`. The draft's market/currency is fixed on creation. `GET /api/v1/builds/{build_id}` returns selections and evaluation intent. PATCH replaces the editable fields and selection snapshot under an expected revision. POST to `/{build_id}/duplicate` copies the exact expected revision into a new independent draft with its own name. DELETE requires `expected_version` and removes only that draft. Mutating calls require allowed Origin and the owning session's CSRF token. Draft storage accepts incomplete selections.

`GET /api/v1/builds/{build_id}/review` returns the draft, catalog evaluation, market-specific offers and per-slot availability using aggregate quantities already in the destination cart. The builder can open this endpoint to show current findings. An eligible review returns a digest over the exact draft, cart revision, evaluation and offer versions/amounts. `POST /api/v1/builds/{build_id}/cart-transfers` requires that digest, both expected revisions and `Idempotency-Key`. It repeats catalog reads outside database locks, checks both revisions under lock and commits the group, line snapshots and receipt together. A repeat of the same request returns the stored receipt even after draft deletion. An explicit new review and key can add a second independent group.

A complete-build transfer requires a compatible evaluation. Explicit parts-only transfers retain the chosen mode and show outstanding findings in review. Both modes require sellable, priced, stock-verified parts. If a review changes, request a fresh review and confirmation. Stock can change after the latest read. Checkout revalidates before reserving. Migration `0006_group_intent` preserves the dedicated-GPU selection with the group.

`POST /api/v1/cart/groups/{group_id}/review` validates a proposed whole group against the expected cart and group revisions. `PATCH /api/v1/cart/groups/{group_id}` repeats that evaluation and requires its digest before updating. Aggregate availability excludes the group's old quantities and includes every other same-SKU selection in the cart. Retained slots keep their line IDs, and changed quantities, variants or price baselines advance the line revision. Removed slots disappear and new slots receive IDs. The saved draft and separate groups retain their own selections. Direct line deletion still allows leaving an incomplete group.

`GET /api/v1/builds/{build_id}/comparison?other_id={id}` compares two distinct drafts owned by the current session in the same market/currency. Both draft revisions, compatibility findings, current display prices and slot differences are returned. Subtotals for components and peripherals are separate and nullable when no prices are known. Each draft retains its selections during an outage, with explicit catalog/evaluation status. The comparison does not edit drafts and its prices are display estimates.

`POST /api/v1/cart/items`, `PATCH /api/v1/cart/items/{line_id}`, `DELETE /api/v1/cart/items/{line_id}` and `DELETE /api/v1/cart/groups/{group_id}` require an allowed Origin, the owning session's `X-CSRF-Token` and expected cart version. Group child edits/deletions also require the group version. DELETE uses version/market query parameters (market defaults to `ir`); POST/PATCH require an explicit market in strictly typed JSON. All are owner scoped. Mutation receipts return the committed cart version; retrying a stale version returns 409 and never repeats quantities. Request bodies are limited to 16 KiB/10 seconds.

Additions and increases require current sale-enabled, non-reference, priced and stock-verified catalog data. Stock checks aggregate same-SKU quantities across groups and loose lines. They are advisory cart checks, not reservations or checkout guarantees. Decreases and deletion remain available during catalog outages or after a product is removed. Catalog I/O runs outside database locks; the cart version is rechecked under lock afterward. A successful commit returns a receipt without a subsequent upstream request that could obscure success.

Cart reads enrich a coherent line/version snapshot with bounded catalog batches (50 distinct variants, 4 seconds overall, 1 MiB per response). Missing products, unpriced/reference-only/disabled offers, unknown stock, insufficient aggregate stock and upstream outage have separate line statuses. No incomplete response is accepted as a complete price book. On outage, lines remain intact and the full estimate is null. `known_subtotal_minor` sums only currently available lines; `estimated_total_minor` is present only when all lines are available. Totals are decimal integer strings to avoid JavaScript precision loss; an empty cart has total `"0"`. IRR and USD books stay independent. No shipping, tax or compatibility approval is implied.

Migration `0003_observed_price` retains each line's first observed amount/revision. Current values always come from catalog; `price_changed` flags later offer changes instead of freezing prices. Legacy lines without a baseline retain null observed fields. These observations are not checkout quotes or purchase consent. Canonical contracts are `contracts/openapi/cart.json` and generated `apps/web/src/lib/api/cart-schema.ts`; the verification helper checks schema drift.

Run `scripts/Verify-CartFoundation.ps1` with the prepared Linux environment, or pass `-TestImage nivaro-cart:items-test`. Tests use a uniquely named internal network and disposable PostgreSQL memory volume. They verify migration repeatability, schema drift, role/database isolation, group ownership, duplicate line/operation constraints, draft/group separation, aggregate cart limits, guest expiration/cookies, account isolation and bounded authorization failure. `scripts/Verify-IdentityService.ps1` also exercises the real cart authorization client and same-origin guest/login/logout/second-customer requests against both applications and their separate disposable databases. ASGI integration is not browser/gateway acceptance.

The internal mutation module locks the owning cart, compares its expected version and validates the entire proposed snapshot through `validate_quantities` before flushing. Its caller must supply the authenticated owner and an enclosing transaction; it is not a replacement for HTTP authorization or catalog validation. Loose additions preserve same-SKU group lines. Quantity/removal operations address stable line IDs, require a group revision for group children and advance the group revision when changed. Removing a required slot leaves an incomplete group; deleting a group cascades only its own children. Future merge/transfer writers must follow the same lock ordering. A real two-connection test observes the competing PostgreSQL lock and verifies a stale write cannot double quantities.

Default limits are 50 variants, 100 lines and 20 units per variant across all groups and loose lines. Configure them through `CART_MAX_VARIANTS`, `CART_MAX_LINES` and `CART_MAX_UNITS_PER_VARIANT`; database constraints enforce positivity while the aggregate application check uses the configured limits. Saving lines has no stock-reservation effect. Account-cart retention is indefinite until owner deletion or a separately specified retention policy. Physical cleanup of expired guest data is not enabled.

## Private checkout snapshot

Orders reads `GET /internal/v1/orders/carts/{market}?version=…` with a current Identity-issued token for audience `nivaro-cart` and scope `cart.checkout_snapshot`. The signed customer ID identifies the owner. The request takes a shared cart lock, returns 409 if the cart revision changed and returns 404 if the customer has no cart in the selected market. The response preserves line and group IDs, versions, slots and source-build provenance for the catalog quote. It neither creates a cart nor consults cached prices.
