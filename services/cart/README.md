# Nivaro Cart

P05 foundation. The service owns its PostgreSQL database and stores guest/customer owner identities, per-market carts, stable line IDs, component groups, private build drafts and idempotency records. No foreign keys reference another service's database. Transferred group provenance survives source draft deletion. A composite foreign key prevents assigning a line to a group in another cart, and a partial unique index keeps standalone lines unique per variant while allowing that variant in multiple groups.

The service exposes liveness/readiness, `POST /api/v1/cart/session` (guest bootstrap), `GET /api/v1/cart/session` (guest synchronizer token) and `GET /api/v1/cart?market=ir|international` (private owned state). Session bootstrap requires an allowed Origin and `X-CSRF-Request: 1`; reading the token requires that header and rejects foreign origins/cross-site requests. Responses are `no-store`. Guest cookies are random 256-bit values, HttpOnly, SameSite=Lax and Secure in release; only their SHA-256 digest is persisted. Server-side guest CSRF state is independent of the bearer cookie. Thirty inactive days expire ownership without deleting the source cart; explicit expired-session UI recovery and cleanup remain pending.

Customer reads verify RS256 issuer/audience/kind/session claims using identity JWKS, then call the dedicated identity customer introspection route with a short-lived request-bound service credential. Revocation/disable is checked freshly. Origin and session CSRF are validated for future mutating calls. A present invalid/revoked customer cookie or unavailable identity during customer authorization cannot silently fall back to a guest cart. Customer IDs and cart ownership never come from a query parameter or submitted cart ID. The guest cart remains separate after login until the explicit idempotent merge workflow is implemented; logout returns to guest ownership, never to the account cart. The upcoming frontend must coordinate access refresh before cart work for a known signed-in session, because refresh cookies are deliberately restricted to identity's refresh path.

The upcoming runtime configuration must mount a dedicated `cart_identity_service_key` for both `CART_IDENTITY_SERVICE_KEY_FILE` and `IDENTITY_CART_SERVICE_KEY_FILE`. The local secret helper prepares it without changing existing secrets. Do not reuse catalog's service key. No runtime gateway route is enabled at this checkpoint. The state response has stable IDs/versions but no authoritative product summary or price quote yet. Public mutation endpoints, catalog enrichment, merge/transfer transactions, saved-build API and cart UI remain P05 work.

Run `scripts/Verify-CartFoundation.ps1` with the prepared Linux environment, or pass `-TestImage nivaro-cart:ownership-test`. Tests use a uniquely named internal network and disposable PostgreSQL memory volume. They verify migration repeatability, schema drift, role/database isolation, group ownership, duplicate line/operation constraints, draft/group separation, aggregate cart limits, guest expiration/cookies, account isolation and bounded authorization failure. `scripts/Verify-IdentityService.ps1` also exercises the real cart authorization client and same-origin guest/login/logout/second-customer requests against both applications and their separate disposable databases. ASGI integration is not browser/gateway acceptance.

The internal mutation module locks the owning cart, compares its expected version and validates the entire proposed snapshot through `validate_quantities` before flushing. Its caller must supply the authenticated owner and an enclosing transaction; it is not a replacement for HTTP authorization or catalog validation. Loose additions preserve same-SKU group lines. Quantity/removal operations address stable line IDs, require a group revision for group children and advance the group revision when changed. Removing a required slot leaves an incomplete group; deleting a group cascades only its own children. Future merge/transfer writers must follow the same lock ordering. A real two-connection test observes the competing PostgreSQL lock and verifies a stale write cannot double quantities.

Default limits are 50 variants, 100 lines and 20 units per variant across all groups and loose lines. Configure them through `CART_MAX_VARIANTS`, `CART_MAX_LINES` and `CART_MAX_UNITS_PER_VARIANT`; database constraints enforce positivity while the aggregate application check uses the configured limits. Saving lines has no stock-reservation effect. Account-cart retention is indefinite until owner deletion or a separately specified retention policy. Physical cleanup of expired guest data is not enabled.
