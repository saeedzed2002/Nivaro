# Support service

Include `compose.support.yaml` with the base Compose file. Run `scripts/Initialize-LocalSecrets.ps1` to provision its PostgreSQL password, Identity service key and dedicated Redis password. The gateway routes the browser API, and the private Identity session check stays on the Compose network. Support Redis uses its own internal network and an account restricted to the chat notification channel.

Customers create and list their conversations under `/api/v1/support/conversations`. Conversation creation accepts a stable `client_conversation_id`. Both conversation scopes support `GET` and `POST` at `/{conversation_id}/messages`. History is ordered by sequence and accepts `after` and `limit`. A retry with the same sender, conversation, client message ID and text returns the committed original. Each sender may commit up to five new messages in a rolling second across conversations.

Staff use `/api/v1/admin/support/conversations`. Support agents see their assignments and the claimable queue. Reading or sending messages requires the assignment unless the caller is a super administrator. Staff claim and super administrators reassign through `PUT /{conversation_id}/assignment`. Use the current version for changes, including `PUT /{conversation_id}/status`. Closing records the time and prevents new messages. Committed history remains available to authorized participants.

The browser connects to `/ws/support` using its same-origin access cookie. Use subprotocol `nivaro.support.customer.v1` for customer sessions or `nivaro.support.staff.v1` for staff sessions. A connection without a subprotocol uses the customer scope. Configure `SUPPORT_ALLOWED_ORIGINS` as an exact JSON allowlist alongside the corresponding Identity origins.

Use `conversation.subscribe` for the selected conversation. Its `sync.result` returns initial history and the subscription replaces the previous selection for that socket. Subsequent `message.created` frames contain committed messages. Use `sync.request` to fill gaps and periodically resynchronize. Reconnect with `conversation.subscribe` and your last applied sequence as `payload.after`, starting at zero. A `sync.result` contains at most ten messages. If `has_more` is true, request the next page after the last contiguous sequence. Deduplicate by message ID when merging history, live pushes and acknowledgments. `message.accepted` confirms database commit. Keep the same `client_message_id` when retrying an unacknowledged send and issue a new `request_id` for each attempt. Match errors against the echoed identifiers. Both versioned schemas are in `contracts/websocket/`.

The server checks the session for every operation and after each 25-second wait for an incoming frame. Reconnect after HTTP refresh when the server closes with `4401`. A `4403` closure means the session lost permission. A `1013` closure calls for backoff. The transport uses a 25-second ping interval and a 35-second pong timeout. Client text messages have a 16 KiB limit.

Send `message.read` with `payload.sequence` set to the highest visible contiguous message in the selected conversation. The server rejects sequences ahead of persisted history and stores each participant's highest value. History and `sync.result` contain the caller's cursor and the current counterpart's cursor. Live `message.read` frames carry the same pair, with a null request identifier for notifications. For a customer, the counterpart is the assigned agent.

After subscribing to a conversation, the browser sends `presence.changed` with `payload.active: true` at entry and every eight seconds. Presence expires after 24 seconds without renewal. `typing.changed` takes the same boolean payload and expires five seconds after the last typing update. A clean disconnect removes only that connection's activity, so another open tab can keep the participant present. Peer notifications carry `payload.expires_in_ms` and the browser clears the indicator when the duration elapses. Only the conversation owner and currently assigned agent share activity in an open or waiting conversation. Redis stores the activity leases independently of history.

Each committed message has one private outbox row. A replica claims the row and publishes a conversation UUID through Redis. Read cursor rows likewise track the sequence last published and can combine multiple advances into one notification. All subscribed replicas recheck permissions and retrieve committed messages and cursors from PostgreSQL. While Redis is unavailable, sends and read updates still commit if Identity and PostgreSQL are reachable. Clients can synchronize during the interruption and active subscriptions catch up after Redis reconnects. Retention execution remains subsequent P09 work. Use `scripts/Verify-SupportFoundation.ps1` to check the exported schemas and exercise two disposable replicas, including an outage of their shared Redis connection.
